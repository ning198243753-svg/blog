# 部署文档（M5）

本文档面向**全新服务器**（Ubuntu 22.04）+ **Docker Compose** + **HTTPS 自动证书**。

---

## 一、先读这一段：哪些验证过，哪些没有

**这是本文档最重要的一节。**

开发机（Windows）上**没有安装 Docker**，所以：

| 内容 | 验证状态 |
| --- | --- |
| 前端能用 `pnpm@10.15.0` + `--frozen-lockfile` 完整构建 | ✅ **实测通过**，产物文件名哈希与本地一致 |
| 部署配置之间自洽（10 类共 40 项检查） | ✅ **实测通过**，且故意注入 3 个故障确认能抓到 |
| `deploy.sh` 的 bash 语法 | ✅ **实测通过**（`bash -n`） |
| 行尾符（CRLF 会让脚本无法执行） | ✅ **实测通过**，已全部为 LF |
| **Dockerfile 能构建出镜像** | ❌ **未验证**（无 Docker） |
| **容器能启动、服务能互通** | ❌ **未验证** |
| **Nginx 配置能被 Nginx 接受** | ❌ **未验证** |
| **HTTPS 证书能申请成功** | ❌ **未验证** |

**所以第一次部署时，请把下面每个命令的输出都看一眼**，不要假设它成功了。
`deploy.sh verify` 会在关键节点主动检查并报错，但首次部署仍建议人工确认。

> **为什么不在开发机上装 Docker 来验证？**
> 那是可以做的，但会引入一个新的问题：Windows 上的 Docker Desktop 用 WSL2
> 虚拟化，网络模型与 Linux 服务器差异很大 —— 卷权限、`host.docker.internal`、
> 文件系统大小写敏感性都不同。**在 Windows 上验证通过，反而会给你一种
> 虚假的安全感**，而真正的差异会在服务器上暴露。
> 更可靠的做法是把验证做在目标环境上。

## 二、准备服务器

### 2.1 装 Docker

```bash
# 官方脚本。它会自动识别发行版并配置软件源。
curl -fsSL https://get.docker.com | sh

# 【为什么要加这个组】不加的话每条 docker 命令都要 sudo，
# 而 sudo 会让「docker compose exec」这类交互命令更繁琐。
sudo usermod -aG docker $USER
# 重新登录使组生效
```

验证：

```bash
docker --version
docker compose version      # 注意是 "docker compose"（空格），不是 "docker-compose"
```

### 2.2 把代码放到服务器

```bash
sudo mkdir -p /opt/blog && sudo chown $USER:$USER /opt/blog
git clone https://github.com/ning198243753-svg/blog.git /opt/blog
cd /opt/blog
```

> **如果仓库是私有的**，用 deploy key 或 personal access token。
> 不要用密码 —— 那会留在 shell 历史和 `.git/config` 里。

### 2.3 配置环境变量

```bash
cd /opt/blog/backend
cp .env.example .env
chmod 600 .env          # 含密钥，只允许属主读写
```

然后编辑 `.env`，**必须改这两项**：

```bash
# 生成一个随机密钥：
#   python3 -c "import secrets; print(secrets.token_urlsafe(48))"
SECRET_KEY=<粘贴上面生成的值>

# 管理员密码，自己定一个强密码
ADMIN_PASSWORD=<你的密码>
```

**为什么 `SECRET_KEY` 不能留示例值**：它用来签名会话 Cookie（ADR-03）。
示例值写在公开仓库里，任何人拿它就能伪造一个"已登录"的 Cookie ——
**不需要知道你的密码。**

### 2.4 确认域名解析

```bash
dig +short 你的域名
# 应该返回服务器 IP。没有返回就先等 DNS 生效，或检查 A 记录。
```

**这一步必须在申请证书之前完成。** Let's Encrypt 通过 HTTP 访问你的域名来验证归属，
解析没生效时申请会失败，而且失败多次会触发速率限制（**同一域名每周 5 次**），
等待期很长。

### 2.5 替换 Nginx 配置里的域名

```bash
cd /opt/blog
sed -i 's/__DOMAIN__/你的域名/g' nginx/nginx.conf
grep -n "server_name\|ssl_certificate" nginx/nginx.conf    # 确认替换结果
```

## 三、首次部署

### 3.1 先启动 HTTP（申请证书需要）

证书申请要求域名能通过 80 端口访问，而现在的 `nginx.conf` 里 443 需要证书文件 ——
**证书还没有，Nginx 会因为找不到文件而启动失败。**

**这是一个先有鸡还是先有蛋的问题**，解决办法是分两步：

```bash
cd /opt/blog

# 用一份「只有 HTTP」的临时配置启动，专门用来完成 ACME 挑战
cat > /tmp/nginx-bootstrap.conf <<'EOF'
server {
    listen 80;
    server_name _;
    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }
    location / {
        return 200 "bootstrap\n";
    }
}
EOF

# 临时替换配置并启动
cp nginx/nginx.conf nginx/nginx.conf.real
cp /tmp/nginx-bootstrap.conf nginx/nginx.conf
docker compose up -d nginx
```

验证挑战目录可访问：

```bash
curl -I http://你的域名/.well-known/acme-challenge/test
# 【预期】404 —— 这是对的（文件不存在），
# 关键是它由 Nginx 返回而不是连接失败。
# 连接失败说明 DNS 或防火墙有问题，先解决这个再往下走。
```

### 3.2 申请证书

```bash
docker compose --profile certbot run --rm certbot \
  certonly --webroot --webroot-path /var/www/certbot \
  -d 你的域名 \
  --email 你的邮箱 \
  --agree-tos --no-eff-email
```

**成功后确认证书文件存在**（不然下一步还会启动失败）：

```bash
docker compose --profile certbot run --rm --entrypoint sh certbot \
  -c 'ls -la /etc/letsencrypt/live/你的域名/'
# 应该看到 fullchain.pem 与 privkey.pem
```

### 3.3 换回正式配置并完成部署

```bash
cd /opt/blog
cp nginx/nginx.conf.real nginx/nginx.conf
docker compose up -d nginx       # 重新加载配置
./deploy.sh init                 # 构建镜像 + 建库 + 建管理员
```

`deploy.sh init` 会依次做：

1. 检查前置条件（Docker、compose 插件、`.env`、域名是否已替换、`SECRET_KEY` 是否还是示例值）
2. 构建后端镜像（多阶段）
3. 构建前端产物并导出到共享卷
4. **验证产物非空**（防止部署出一个空白站点）
5. 启动 nginx 与 backend
6. **等健康检查通过**（不是"容器在运行"，而是"应用能响应"）
7. 执行数据库迁移
8. 创建管理员账号

### 3.4 验证

```bash
DOMAIN=你的域名 ./deploy.sh verify
```

它会检查：容器状态、`/api/health` 经 Nginx 返回 200、首页 200、
**深层路由回退正常**（history 模式的关键）、HTTPS 200。

**然后人工确认这几件事：**

```bash
# 1. 浏览器访问 https://你的域名，应该看到博客首页
# 2. 访问 https://你的域名/admin/login 登录
# 3. 写一篇带图片的文章并发布，确认图片能显示
# 4. 刷新文章页（验证 SPA 回退与 Cookie 持久性）
# 5. 检查浏览器控制台无错误
```

## 四、证书自动续期

**Let's Encrypt 证书 90 天过期。不自动续期的话，站点会在某天突然无法访问**，
而 HSTS 打开后浏览器连"继续访问"的选项都不给。

服务器上装 cron：

```bash
crontab -e
```

加入：

```cron
# 每天凌晨 3 点检查续期（certbot 只在剩余不足 30 天时才真正续期）
0 3 * * * cd /opt/blog && docker compose --profile certbot run --rm certbot >> /var/log/blog-certbot.log 2>&1

# 续期成功后重载 Nginx（让它读取新证书）
# 【为什么单独一条而不是写在上面】
# certbot 续期成功不等于 Nginx 用了新证书 ——
# Nginx 在启动时把证书读进内存，不重载就一直在用旧的。
15 3 * * * cd /opt/blog && docker compose exec -T nginx nginx -s reload >> /var/log/blog-certbot.log 2>&1
```

**检查续期是否真的在工作**（不要等到证书过期才发现它一直失败）：

```bash
# 手动试跑一次，看输出
docker compose --profile certbot run --rm certbot \
  renew --webroot --webroot-path /var/www/certbot --dry-run

# 定期看日志
tail -20 /var/log/blog-certbot.log
```

## 五、日常运维

### 更新

```bash
cd /opt/blog
git pull
./deploy.sh update
```

它会：先备份 → 记录当前 commit → 构建 → 迁移 → 重启 → 验证。
**验证不通过时会报错退出**，不会留下"看起来更新了"的状态。

### 备份

```bash
./deploy.sh backup
```

**关于 SQLite 的备份必须说清楚**：数据库开了 WAL 模式，
数据分散在 `blog.db`、`blog.db-wal`、`blog.db-shm` 三个文件里。
**在应用运行时直接 `cp` 这三个文件，可能拿到不一致的组合**
（主库是旧的、WAL 是新的），恢复到这种备份上数据会缺一部分且难以察觉。

所以 `deploy.sh backup` 用了 SQLite 的 `VACUUM INTO` ——
它让数据库自己生成一份一致的单文件快照，不受并发写入影响。

**备份放在 `./backups/`，只保留最近 10 份**（磁盘有限，撑满磁盘的表现是
"应用突然写不了数据库"，很难联想到备份）。

### 回滚

```bash
./deploy.sh rollback
```

**它不做的事**：不自动回退数据库迁移。
降级迁移可能丢数据，而且很多迁移的 `downgrade()` 写得并不严谨。
需要回退迁移时手工执行并先确认数据安全：

```bash
docker compose exec backend python -m alembic downgrade -1
```

### 查看状态

```bash
./deploy.sh status      # 容器状态 + 磁盘占用 + 最近备份
docker compose logs -f backend
```

## 六、这份配置里几个关键取舍

### 6.1 只有 Nginx 暴露端口

`backend` 没有 `ports` 映射，只在 Docker 内网被 Nginx 访问。

**这不只是"更安全"的问题。** 后端 Dockerfile 里用了
`--forwarded-allow-ips "*"`（信任所有来源的 `X-Forwarded-*` 头），
这个设置**只有在后端不对公网暴露时才是安全的**。

如果哪天给 backend 加了 `ports: "8000:8000"`，它立刻变成漏洞：
任何人直连 8000 并伪造 `X-Forwarded-For` 就能冒充任意 IP ——
限流、审计日志、封禁全部失效。

**要加端口映射，必须同时改 Dockerfile 里的 `--forwarded-allow-ips`。**

### 6.2 前端在服务器上构建

服务器只装 Docker，但构建前端需要 Node 环境 —— 这由**构建阶段**提供，
构建完那个阶段就被丢弃，最终镜像里没有 Node。

**代价**：服务器首次构建需要下载 Node 镜像与 npm 依赖，
在 3Mbps 带宽下这一步可能要几分钟。

**为什么不在本地构建好再上传**：本地没有 Docker，构建不出 Linux 镜像。
而且即使有，镜像的传输量（含 Python 依赖，约 200-300MB）通常也大于
"传源码 + 服务器上构建"。

### 6.3 HSTS 从 1 天开始

`nginx.conf` 里是 `max-age=86400`（1 天），不是常见的 1 年。

**理由**：HSTS 一旦生效，浏览器在有效期内**强制**用 HTTPS，
用户无法点击"继续访问"绕过。如果证书出问题（比如续期失败），
站点会彻底无法访问，只能等 max-age 过期。

**先跑 1 天，确认 HTTPS 稳定运行几周后，再逐步调大**（常见终值 1 年）。
配置模板里常见的"一上来就 1 年"把"证书配置出错"的代价从
"浏览器警告"放大成"站点无法访问"。

### 6.4 index.html 不缓存，带哈希的资源缓存一年

- `/assets/`（文件名含内容哈希）→ `Cache-Control: public, immutable`，1 年
- `/index.html` → `no-cache`（每次都向服务器确认，未变返回 304）

**这个组合如果写反了会怎样**：
`index.html` 被缓存的话，它引用的还是旧的文件名，
**部署新版本后用户看到的仍是旧页面，而且刷新无效**。

### 6.5 上传图片由 Nginx 直接返回

`/uploads/` 走 `alias /data/uploads/`，不经过 FastAPI（ADR-02）。

**原因**：图片是纯静态文件，让 Python 进程读文件再写响应体，
会白占一个有限的工作进程。图片一多，"加载图片慢"会拖累"接口慢"。

**安全措施**：用一个白名单正则 `^/uploads/[^/]+\.(webp|jpg|jpeg|png|gif)$`，
字符类 `[^/]+`不接受斜杠，所以 `/uploads/../etc/passwd` 这类路径
**根本匹配不上**，会落到后面的 `return 404`。

用字符类做路径穿越防护比写 `if ($request_uri ~* "\.\.")` 更可靠 ——
后者是 Nginx 社区公认容易出错的做法（`if` 在 `location` 里的求值时机与直觉不符）。

## 七、出问题时先看这里

| 现象 | 最可能的原因 |
| --- | --- |
| `syntax error near unexpected token $'{\r''` | 脚本是 CRLF 行尾。见 `.gitattributes`，或 `sed -i 's/\r$//' deploy.sh` |
| 登录成功但下一步又变未登录 | `COOKIE_SECURE=true` 而用户在用 HTTP 访问。确认走 HTTPS |
| 部署后仍是旧页面 | `index.html` 被缓存了。检查 `/index.html` 的 location |
| 刷新文章页 404 | SPA 回退失效。检查 `try_files $uri $uri/ /index.html;` |
| 上传大图返回 413 | Nginx 的 `client_max_body_size` 小于应用限制，请求到不了 FastAPI |
| 图片 404 | nginx 容器没挂 `blog_data:/data`，或 `alias` 路径不对 |
| 容器重建后文章没了 | 数据库写到了容器可写层。检查 `DATABASE_URL` 是不是 4 个斜杠的绝对路径 |
| `docker compose` 报 unknown command | 用的是旧版 `docker-compose`（连字符）。需要 Docker 20.10+ 的插件形式 |
| 证书申请失败且提示速率限制 | 同一域名每周 5 次。用 `--dry-run` 测试，不要盲目重试 |

## 八、部署后建议做的事

1. **配一个监控**：定时访问 `/api/health`，失败时通知你。
   单机部署没有冗余，磁盘满、内存耗尽都需要提前知道。
2. **设置日志轮转**：Docker 日志默认不限制大小，长期运行会占满磁盘。
   ```bash
   # /etc/docker/daemon.json
   { "log-driver": "json-file", "log-opts": { "max-size": "10m", "max-file": "3" } }
   ```
   改完需要 `sudo systemctl restart docker`。
3. **确认防火墙**：只开放 22（SSH）、80、443。
   ```bash
   sudo ufw allow 22 && sudo ufw allow 80 && sudo ufw allow 443 && sudo ufw enable
   ```
   **注意**：Docker 会自己修改 iptables，`ufw` 对容器端口的控制可能不生效。
   由于本项目只映射了 80/443，实际影响有限，但不要依赖 ufw 来保护容器端口。
4. **把备份拷到别处**：同一台机器上的备份挡不住磁盘损坏。
